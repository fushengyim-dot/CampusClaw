# 第4课问答资料发送上限设计

## Context

`backend/handlers/ask.go`当前固定以4条命中检索，并将所有返回命中写入对话消息。前端`frontend/src/App.tsx`只说明“最多4段”，请求体不含逐次上限。历史真实测试证明：固定上限不足以表达一次具体授权仅允许1段的场景。

## Decisions

### D1：请求上限由用户逐次选择并由服务端执行

- 新增可选整数`max_evidence_chunks`，范围1—4。
- 缺省值为1，作为遇到旧客户端或缺字段时的保守行为。
- 前端提供1、2、3、4段选择器，初始选择1；页面在发送前显示将送到课程对话服务的上限。
- 服务器检索仍最多取4条以保持排序候选稳定，随后在组装模型消息之前截断至所选上限。
- 超范围、非整数、负数或零值返回400；此时不调用对话服务。

### D2：服务端回显实际数据量

成功响应添加`evidence_count`和`max_evidence_chunks`。`evidence_count`是最终传给`ChatCompleter`的命中条数，也是返回`citations`的条数；由服务端计算。

### D3：不改变原有检索/失败边界

检索继续取会话中的真实`class_id`和本轮问题。无命中仍返回固定无结果文案、空引用和计数0，不调用模型。检索失败仍返回503，不伪装为无命中。任何本变更测试只使用本地stub。

## Risks / Trade-offs

- 默认1会减少旧客户端一次请求最多发送的资料数；这是本次已记录范围偏差后的安全默认值。需要更多上下文的操作必须在页面明确提高上限。
- 上限只能限制资料段数，不代表用户授权发送了某一特定段正文；真实外发仍受用户当次操作和项目级授权约束。
- 原始课程第4课spec仍不可读，课程方后续提供原文时需再对照。

## Acceptance approach

使用本地ChatCompleter stub检查多命中情况下消息和引用严格不超过1、2、4段；验证缺省值、无命中、非法上限以及检索/模型失败；前端构建并手动查看页面选择器和成功计数。全过程不连接课程模型。
